# Pre-rewrite baseline (velvet/exonerate `addsv`)

Captured on the assembly-based SV engine, before it is replaced by the
reference-templated one, so the new engine can be diffed against it.

Reproduce with `scripts/setup_env.sh` (which installs velvet and exonerate) and:

```
cd test
python3 -O ../bin/addsv.py -p 4 -v ../test_data/test_sv.txt \
  -f ../test_data/testregion_realign.bam -r $REF \
  -o ../test_data/baseline/sv_mut.bam --aligner mem --keepsecondary \
  --seed 1234 --inslib ../test_data/test_inslib.fa --vcf ../test_data/baseline/
```

BAMs are gitignored (~11 MB each); the truth VCFs and validator TSVs are kept.

## Why INV and DUP were dropped

Both are 13,711 bp, so `addsv.main()` promotes them past the 10 kbp threshold to
`BIGINV`/`BIGDUP`. The `BIG*` path pads the interval by `--minctglen` (4000 bp)
either side and assembles it, and velvet returned a contig containing `N`:

```
WARNING  ... is over 10kbp long: converting to use BIGINV instead.
WARNING  22_34071043_34071043_BIGINV contig dropped due to ambiguous base (N), aborting mutation.
```

**The reference has zero `N` in any of these intervals** (verified with
`samtools faidx` over `22:34067043-34075043`, `22:34280754-34288754` and the
full spans: `N=0` in all four). Velvet inserts `N` runs when it scaffolds a
`-shortPaired` library across a coverage gap, so the ambiguous bases are an
artifact of the assembler, not a property of the locus.

A reference-templated engine cannot reproduce this failure: it copies reference
bases, which are `N`-free here. This is the concrete cost of the assembler, and
the reason `--allowN` becomes a cheap pre-check rather than a post-assembly
discovery.

Note also that the two aborted jobs left **0-byte log files** rather than
surfacing an error, and `addsv` exited 0. The truth VCF is generated by scanning
those logs, so a dropped mutation is indistinguishable from one that was never
requested.

## Caveat on what the validator checks

`validate_spikein.py` checks **BAM against truth VCF**. It cannot see the 802 bp
and 1798 bp coordinate errors above, because the truth VCF records the position
the tool actually produced, not the one that was requested — the DEL row is
`OK` precisely because BAM and VCF agree with each other while both disagree
with the input.

Comparing truth VCF POS against the *input* varfile is a separate assertion, and
it is the headline acceptance test for the reference-templated engine: output
POS must equal input POS exactly for DEL/DUP/INV, and breakends must equal the
requested breakends for BND.
